1. アプリケーション概要・目的

  • 愛称: ホビめぐ。ヘッダー・ブラウザのタブ・アプリ名メタデータに使用し、「全国中古＆ホビーショップ巡りマップ」を説明名として併記する。
  • 目的: Googleマップをベースに、ハードオフ、ホビーオフ、駿河屋などの中古ショップまでどのくらいの時間で行けるかが一目でわかり、毎回検索ワードを入力しなくても地図を動かしながら全国の中古ショップを巡れるウェブアプリ。
  • 基本コンセプト:
    • 通常のGoogleマップと同様の操作感で扱えること。
    • オプション画面から 「店舗チェーンのオン・オフ」「扱っているカテゴリリストのオン・オフ」「アクセス手段の選択」 ができること。
    • 画面内に表示されている全店舗への「おおよその所要時間」を常時一括表示し、クリック時には経路と予測所要時間を表示できること。
    • 地図上の店舗ピンは、ハードオフ公式アプリの店舗検索のように 「どの位置にどの店舗があるか白い吹き出しバルーンの中に各店舗のブランドロゴ看板を縦積み（スタック）表示する形式」 とすること。

2.2 各社ロゴプレート（バルーン内表示）

同じピンに統合した店舗は看板を縦積みする。全40業態の表示枠は当初の横74：縦25を共通仕様とし、拡大後の幅96px・高さ約32.43pxで統一する。SUPER BAZAAR・PLUS・正方形ロゴも枠の縦横比を変えない。ロゴ自体はobject-fit: containで形を保って収める。プレート内に上下3px・左右6pxの背景色の余白、白い吹き出しに3pxの外余白と看板間隔を残す。

公式SVGがあるものはパスを利用する。ラスター原本は出典確認用に無加工で保存し、表示用は輪郭を曲線パスへ変換したSVGを使用する。PNG/JPEGをSVGに埋め込むだけの変換は行わない。メロンブックスなどの画像内の不要な余白は表示用SVGの範囲から除く。画像の出典、確認日、原本と表示用のSHA-256、変換内容はpublic/brands/sources.jsonに記録する。

ハードオフ系列と通常BOOKOFFは指定の業態パネル、SUPER BAZAAR・PLUSはそれぞれの参照画像に従う。駿河屋は独立したJPのパスを除き、日本語3文字を表示する。GEOは公式画像の系列共通マークの輪郭をSVG化し、濃紺で表示する。指定配色を優先し、ロゴの輪郭を保った白抜き・反転配色を許容する。

2.3 ホビめぐのアプリアイコン・ファビコン

採用意匠は「青い角丸四角＋白い地図ピン＋黄色いロボット玩具の顔」。プレビューで承認された案を、小さな表示でも輪郭が保たれるSVGへ整える。顔は2つの青い目と短いアンテナだけで構成し、文字・巡回矢印・コントローラーは入れない。青は#0877ff、黄は#ffd000、ピンは白。店舗チェーンのロゴとは別のアプリ識別マークとして扱う。

  • 原本: public/favicon.svg（512×512のviewBox）。ヘッダーも同じSVGを32×32pxで表示する。
  • 通常タブ: SVGを優先し、32px PNGと16/32/48pxを内包するICOを代替として指定する。favicon-16x16.pngも生成して保持する。
  • タッチアイコン: public/apple-touch-icon.png（180×180px）。確認・転用向けのpublic/app-icon-512.pngも保持する。これらの追加だけでPWAのインストール機能を提供するものではない。
  • 参照方法: index.htmlでは./favicon.svg等の相対URL、ReactではViteのimport.meta.env.BASE_URLを使い、GitHub Pagesのサブディレクトリに対応する。
  • 実ファイルの表示確認: 明暗背景と16/32/48pxの表示例。
  • 元の検討画像: docs/favicon-concept-2026-10-19.png。各サイズの完成ファイルの原本はSVGとし、提案ボードの画像を切り抜いてタブへ表示しない。

再生成はscripts/build_app_icons.cjs（npm run build:icons）で、SVGからPNGとICOをまとめて作る。SVG変更時は生成済みファイルも同じコミットに含める。生成時だけNode.jsのsharpが必要で、通常のアプリ実行・CIビルドでは同梱済みファイルを使用する。手動環境で必要な場合はnpm install --no-save --package-lock=false sharpを実行してから生成する。

3.2 アクセス手段の選択と概算所要時間

一覧・地図ピンの一括計算はルートAPIを呼ばず、estimateTravelInfoの距離モデルを使用する。地図表示や選択店舗の経路検索のAPI利用とは区別する。直線距離は地球半径6,371kmのHaversine式、推定道路距離は $d=d_{straight}\times f$（km）。速度モデルは次の通りで、交通状況・実際の道路形状を取得した値ではない。

ID 表示名 迂回係数 f 近距離速度 km/h 中長距離速度 km/h 初期時間 分
DRIVING_TOLL 車（有料道路優先） 1.28 36 68 3
DRIVING_NO_TOLL 車（一般道優先） 1.32 28 34 3
TRANSIT 公共交通機関（電車・バス） 1.25 26 45 10
BICYCLING 自転車 1.22 15 15 1
WALKING 徒歩 1.2 4.5 4.5 0

丸め前の所要時間 $T$（分）は次の式。最終値は全モードで $\max(1,\mathrm{round}(T))$ とする。

モード 計算式
有料道路優先 $3+60\min(d,8)/36+60\max(d-8,0)/68$
一般道優先 $3+60\min(d,12)/28+60\max(d-12,0)/34$
電車・バス $d<1.2$なら $60d/4.5$、それ以外は $10+60\min(d,10)/26+60\max(d-10,0)/45$
自転車 $1+60d/15$
徒歩 $60d/4.5$

選択店舗のルートを取得した場合は同じ出発条件の単店結果を5分間優先する（7章）。一般道優先のGoogle検索はavoidHighways・avoidTollsを共にtrueにし、有料道路優先は共にfalseにする。これらは検索条件であり、必ず高速道路を使う／完全に回避する保証ではない。

所要時間上限スライダーは15〜150、15刻み。15〜135はその分数以内、150は「制限なし」。初期値は150。表示距離は10km未満を小数1桁、10km以上を整数で示す。

3.3 所要時間の表示方式・閉店間に合うか判定・初回GPS仕様

  • 初回オープン時の自動現在地（GPS）取得:
    • アプリを開いた際、自動的にブラウザの navigator.geolocation.getCurrentPosition で現在地（GPS）の取得を試み、取得できた場合は「現在地 (GPS)」を出発地および地図の初期表示中心に設定する。現行実装では保存済み出発地があってもGPS取得成功時はそちらを優先する。位置情報の利用が拒否された場合や非対応環境では、初期位置（東京・秋葉原駅周辺など）をそのまま維持する。
  • スマートフォン表示時の固定レイアウト:
    • スマートフォンで地図をドラッグ・ピンチ操作した際に上部ヘッダーや下部タブバーが画面外へスクロールして消えないよう、外側のページスクロールを抑え、#rootの高さを100dvhにしてヘッダーと下部ナビの領域を維持し、モバイル幅ではヘッダー要素を1行にコンパクト収容する。またモバイル時は下部ナビゲーションバー（⚙️ オプション / ▤ 地図＋一覧 / 🗺️ 地図のみ / 📋 一覧）で4種類の表示を切り替える。初期表示は地図＋一覧で、上部44%を地図、下部を独立スクロールできる店舗一覧に使う。オプションを閉じると直前の閲覧レイアウトへ戻る。一覧のみで経路を選択した場合は地図＋一覧へ切り替え、選択した経路をその場で表示する。
  • 常時一括表示（概算）と到達圏サークル:
    • 画面内に表示されている全店舗への「おおよその所要時間」を、地図上のバルーン上部および右側の店舗一覧リストに常時表示する。
    • オプションでバルーン上の時間表示のON/OFF、および出発地からの到達時間目安サークル（15分圏: 緑 #10b981 / 30分圏: 青 #3b82f6 / 60分圏: オレンジ #f59e0b の同心円）のON/OFFが可能。
    • サークル半径はMapCanvas.tsxの簡易モデルで、分数をtとすると有効移動分はmax(2, t - startupMinutes)。15分は近距離速度、30分・60分は近距離速度と中長距離速度の平均を使い、時間×速度を迂回係数で割って直線半径へ換算する。実際の道路形状・渋滞・時刻表は反映せず、3.2の個別店舗の区間別速度モデルとも計算方法が異なる。到達範囲を保証する円ではない。
  • 閉店時間を考慮した「間に合う / ギリギリ / 間に合わない」リアルタイム判定:
    • 各店舗の営業時間（例: 10:00～20:00, 10:00～24:00, 10:00～25:00 等の深夜24時超え表記、24時間営業）を正規表現でパースし、出発時刻（端末のローカル現在時刻を30秒周期で更新、または任意指定時刻）＋各店舗への移動所要時間（ルート検索済みの場合は取得した予測所要時間、未取得・キャッシュ失効時は距離に基づく概算所要時間）から、到着予定時刻 と 閉店までの残り時間 を全店舗リアルタイムに自動計算する。
    • 判定区分:
      • 🟢 間に合う (open_ok / open_24h): 到着時点で閉店まで30分以上の余裕がある店舗（または24時間営業店）
      • 🟠 ギリギリ (closing_soon): 閉店前には到着できるが、閉店まで残り30分未満の店舗（ピン上にも 🟠残XX分 と警告表示）
      • 🔴 間に合わない (closed_on_arrival): 到着予定時刻にはすでに営業終了している店舗（ピン上にも 🔴閉店 と表示し、バルーンを半透明グレースケール化）
      • 🔵 開店前着 (before_open): 朝早い出発等で開店時刻より前に到着する店舗
      • ⚪ 時間情報なし (unknown): 営業時間が未登録または不定休表記のみの店舗
    • 営業日のカレンダー・祝日・臨時休業・複数の曜日別時間帯を完全には解析しない。原文をNFKC正規化し、最初の時刻範囲を目安に判定する。情報なし／解析不能と開店前着は閉店除外フィルタでも残す。
    • オプション画面にて 「出発時刻の指定（現在時刻 / 時刻指定）」 および 「🔴 閉店に間に合わない店舗（到着時営業終了）を非表示にする」 フィルタのON/OFF切り替えが可能。

3.5 ルート・到着予測表示・巡回ハシゴルート（ツアービルダー）の最近傍法自動最適化

  • 単一店舗へのルート・到着予測表示:
    • 店舗バルーンまたは店舗カードの「🚗 ルート表示」をクリックすると、Google Mapsの現行Routes APIを優先し、旧Directions API、モード対応のOSRM、距離モデルの順に切り替えて経路線を描画し、算出条件を明示した予測所要時間・移動距離・到着予定時刻・閉店判定を左下のルート案内カードに表示する。
  • 複数店舗の巡回ハシゴルート（ツアービルダー）:
    • 各店舗カードの「➕ 巡回追加」ボタンで最大 8店舗 までハシゴ候補リストに追加可能。
    • 「✨ 最適ルート計算」実行時、出発地から簡易距離が最も近い未訪問店舗を順次選択する 最近傍法（Nearest Neighbor Heuristic） により訪問順序を自動で並び替えた上で、訪問順に区間を計算して合計所要時間・総移動距離を算出する。訪問順の判定には緯度・経度の差をMath.hypotへ渡す簡易距離を使い、区間の所要時間は並べ替え後に経路サービスで取得する。Google検索は各区間の到着予測を次区間の出発時刻にする。最短時間・最短距離の保証はなく、店内滞在時間や開店待ち時間は加算しない。
    • ルート案内カードの「↗ Googleマップナビで開く」ボタンから、出発地・全経由地・最終目的地・移動手段パラメータ（travelmode）をセットした本家GoogleマップナビURL（https://www.google.com/maps/dir/?api=1&...）を別タブまたはスマホアプリで直接起動できる。一般道優先ではavoid=tolls,highwaysも付ける。指定出発日時はこのURLへ渡していないため、外部ナビの結果が本画面と一致する保証はない。

3.6 表示中エリアの新規店舗スキャン

ヘッダーまたはマップの探索ボタンから実行する。緯度方向の表示幅が1.5度を超える場合は検索せず、地図拡大を案内する。範囲を自動で縮めて検索する動作ではない。

  1. Google MapsとPlacesが利用可能なら、ハードオフ・ホビーオフ・オフハウス・駿河屋・ブックオフ・らしんばん・まんだらけ・古本市場・お宝創庫・鑑定団の10キーワードで順次textSearchを実行する。ページ送りは行わない。

  3. 既存または今回発見した店舗との直線距離が120m未満の候補は、店名にかかわらず重複として追加しない。採用店はclassifyShopByNameでチェーンと看板を付ける。

3.7 店舗情報の更新と端末への保存範囲

店舗情報の永続的な更新はGitHub Actionsによる配布DBの更新に一本化する。ブラウザの店舗編集・手動追加・削除のUI、編集モーダルおよび保存処理は撤去した。利用者向けのJSON読込・書き出しインタフェースは提供しない。自動更新用JSONの形式・生成・配信は6章のとおり継続する。

現在使用するlocalStorageの保存キーは以下の2種類に限定する。

  1. REUSE_MAP_USER_PREFS_V1: ユーザーの閲覧設定（出発地、移動手段、所要時間上限、ピン時間表示、到達圏サークル表示、出発時刻の方式と指定値、閉店除外フラグ、有効チェーン、保存時の全チェーン一覧knownChains、有効な親カテゴリ・詳細サブジャンル、OR/ANDモード）。チェーン設定の移行は11章、旧カテゴリ設定の移行は3.8に従う。
  2. REUSE_MAP_GOOGLE_API_KEY: ユーザーがブラウザ上で設定したGoogle Maps APIキー。

旧版のREUSE_MAP_CUSTOM_SHOPS_V1・REUSE_MAP_EDITED_SHOPS_V1・REUSE_MAP_DELETED_IDS_V1は読み書きしない。保存値自体は消去しないが、旧編集・追加・削除を配布DBへ合成せず、自動更新の結果が端末別の情報で上書きされたり、旧削除指定によって店舗が隠れたりしないようにする。起動時はfetchShopsDatabaseで配布データを検証し、有効な同一IDは先頭1件だけ採用する。

周辺探索で発見した店舗は3.6の一時表示として扱う。GitHub Issueへの自動送信は未実装。現行の静的配信構成には送信を認証するサーバーがなく、共有トークンをフロントエンドへ埋め込む設計は採らない。Issue入力画面への引き継ぎだけでは自動送信にならないため、代替の報告UIも設けない。

4.2 複合店舗（同一敷地・同一ビル）の空間クラスタリング統合アルゴリズム

  • 新規PC専門4チェーン、手芸チェーン、イエローサブマリン、ポポンデッタ、お宝あっとマーケットは距離だけでは統合しない。秋葉原などでの別住所・別支店の混同や異業態の混同を避けるため、公式店舗IDごとのピンを維持する。
  • 従来チェーンはハードオフグループ内での同一住所キー統合に加え、チェーン横断で 緯度・経度の差がそれぞれ 0.0006度未満（緯度方向で約65m） にある店舗を複合店舗の候補として1つのピンに自動統合する。これは敷地・建物の一致を実証する判定ではなく、近接した別店舗をまとめる可能性がある。
  • 統合時には chains・brands・categories・subCategories をマージし、吹き出しバルーン内のブランドプレートは定義順（BRAND_ORDER）に従って縦積み（スタック）表示する。また、ハードオフFCのブックオフ情報とブックオフ公式APIの BOOKOFF SUPER BAZAAR / BOOKOFF PLUS 情報が同一地点で重なった場合は、より詳細な bookoff_sb / bookoff_plus プレートを優先して重複表示を排除する。

4.3 店舗情報の定期自動更新パイプライン（GitHub Actions 定期バッチ ＆ フォールバック保護）

公式一覧・取得できた営業時間・店舗別品目を定期的に更新する。取得先の掲載範囲と障害時保持により、すべての項目が毎回最新になる保証はない。以下の自動更新機構を備える：

  1. 統合データ更新スクリプト (scripts/update_all_official_data.py / npm run update-data):
    • 駿河屋（リアルストア・フレンドリーショップ）、ハードオフグループ全店、ブックオフ公式API、ゲオ公式全店、らしんばん公式API、古本市場・ふるいち公式、お宝創庫公式、およびupdate_pc_shops.pyのPC専門4チェーンから最新の店舗一覧を一括取得する。
    • 安全ガード（フォールバック保護）: 各チェーンごとに最小期待店舗数（min_expected_count）を設け、万が一取得先サイトのメンテナンスや一時的な通信エラーで取得件数が閾値を下回った場合は、既存のスナップショット（scripts/official_*.json）を自動で維持し、データ欠損を防止する。
    • 国土地理院ジオコーディングキャッシュ (scripts/gsi_geocode_cache.json): 既存店舗の住所座標はキャッシュから即時解決し、新規オープンした未知の住所のみ 国土地理院APIへ問い合わせることで、API負荷を抑えつつ高速に data/shops.json と public/data/shops.json を再生成する。
  2. GitHub Actions 定期自動実行ワークフロー (.github/workflows/update-shops.yml):
    • 定期スケジュール実行 (schedule): 毎日 03:00 JST（前日 18:00 UTC、cron: "0 18 * * *"）に自動で python scripts/update_all_official_data.py を実行する。
    • 手動即時実行 (workflow_dispatch): GitHubリポジトリの「Actions」タブから任意のタイミングで手動トリガー可能。
    • 自動コミット＆GitHub Pages再デプロイ: 店舗データに差分（新店追加・閉店除外・営業時間更新など）が検出された場合、github-actions[bot] が自動で data/shops.json / public/data/shops.json をリポジトリへコミット＆プッシュし、そのまま本番バンドル（npm run build）をビルドして GitHub Pages を最新データへ更新する。

    • 各社公式店舗案内ページの営業時間テキストを取得。
  • 手芸3チェーン（ユザワヤ・クラフトハートトーカイ・オカダヤ）:
    • 各社公式店舗詳細ページ記載の営業時間（例: 10:00～20:00）を網羅。
  • ホビー・模型専門店（イエローサブマリン・ポポンデッタ・お宝あっとマーケット・鑑定団）:
    • 公式店舗案内記載の営業時間を網羅。
  • OSM補完店舗（アニメイト・メロンブックス・まんだらけ・万代・マンガ倉庫）:
    • osm_supplement.json の opening_hours タグを採用。未設定ノードに対しては各店実態調査に基づく正確な営業時間を付与し、さらにDB構築スクリプト（geocode_and_build.py）にてチェーン別標準営業時間（アニメイト 10:00～20:00、まんだらけ 12:00～20:00、メロンブックス 11:00～20:00、万代 10:00～24:00、マンガ倉庫 10:00～24:00）をフォールバックとして定義。

4.4.2 同一建物・同一住所における複合店舗の営業時間継承ルール

同一敷地・同一建物内に複数業態が同居する複合店（ハードオフ＋オフハウス＋ホビーオフ、またはハードオフ＋ブックオフなど）において、看板ブランドの一部業態のページにしか営業時間が記載されていない場合や、同一番地で個別取得された場合、以下のルールで営業時間を統合・継承する：

  1. 住所キーグループ化時の継承（ho_grouped）: 同一住所キーでグルーピングされる店舗群の中で、少なくとも1つの業態に有効な営業時間（ho_hours）が存在する場合、空文字の業態へ同一の営業時間を共有・適用する（if not g["hours"] and ho_hours: g["hours"] = ho_hours）。
  2. 空間クラスタリングマージ時の引き継ぎ（4.2節）: 近接判定でピンを統合する際、マージ先（主店舗）が営業時間未取得かつマージ元店舗に営業時間がある場合、マージ元の営業時間を引き継ぎ（if not m.get("hours") and s.get("hours"): m["hours"] = s["hours"]）、有効な営業時間が空文字で上書き・消去されることを防ぐ。

4.4.3 表記ゆれの正規化ルール

店舗サイトごとの書式差を吸収し、クライアント側の到着・閉店判定（businessHours.ts）で正確にパースできるよう、DB生成時に以下の正規化を行う：

  • 全角コロンの半角化: 10：00 → 10:00
  • 区切り記号（チルダ・波ダッシュ）の統一: ~ や 〜 をすべて全角波ダッシュ ～ に統一。
  • 24時間営業表記の統一: 24/7 や 24時間 表記を 24時間営業 に統一。
  • 深夜24時超え表記の維持: 10:00～25:00 や 10:00～26:00 等の深夜営業表記はそのまま維持し、クライアントの正規表現パースによって翌日未明として正しく計算される。

6.3 GitHub Actionsでの検証・障害時の動作

  1. Pythonの回帰テストを実行する。CIはPython 3.12を使用する。
  2. 従来系列の公式店舗一覧を取得後、PC専門4チェーンの一覧と販売情報、OSM補完、従来系列の販売品目と追加のフロア等の情報の順に更新する。update_more_assortments.pyはupdate_assortments.py内から呼ぶ。
  3. 従来の一覧は主要文字列・最低件数・前回比85%以上を検証する。最低件数は駿河屋80、FS30、ハードオフ800、ブックオフ500、らしんばん45、古本市場120、お宝創庫35、ゲオ500。PC店は11章の基準を使う。失敗した系列は既存スナップショットを維持する。
  4. OSM補完は80件以上かつ前回の75%以上が必要。取得先はoverpass-api.de、失敗時はoverpass.kumi.systems。両方失敗なら既存補完を維持する。Git管理外のraw_overpass.jsonは不要。
  5. 従来の販売品目更新は成功した店のみ置き換え、失敗店は旧出典・確認日を維持する。PC4チェーンは系列内の全店詳細を検証した上でスナップショットを保存する。最終DBへは採用されたsourceIdsに対応する根拠だけを結合する。
  6. ジオコーディング・統合・品目結合後、最終DBの必須項目・座標・ID一意性・列挙値等と前回比85%以上を検証する。失敗なら公開DB保存前に停止する。従来店の座標未解決は除外される場合があり、ブックオフは公式lat/lonを代用できる。新規PC系列の座標未解決はエラーとして全体のDB生成を止める。
  7. 各JSONは同じディレクトリの一時ファイルから置換する。Windowsの一時的な共有ロックでは最大8回再試行する。複数ファイル全体を一括ロールバックするトランザクションではない。
  8. data/shops.json、public/data/shops.json、座標キャッシュ、official_*.json、OSM補完、ID台帳、販売品目根拠に差分がある場合、botがmainへコミット・pushする。ロゴは対象外。
  9. その後Node.js 22でnpm ci・npm test・npm run buildを実行し、成功した場合のみdistをGitHub Pagesへデプロイする。現行の順序では、Nodeテストやビルドの失敗時も手順8のデータコミットが既に行われている場合がある。失敗した新バンドルは公開しない。

HTTPS通信は証明書・ホスト名検証を有効にする。件数ガードは大幅な欠損の検出用であり、全店の実在・閉店・販売在庫・位置精度を保証しない。公式ページのキャッシュは7日以内の成功分を再利用し、その取得日を保持する。

6.4 ブラウザでの読込と更新の反映

  • アプリの初回マウント時に、配信元と同じ場所の相対URLdata/shops.json?v=<現在時刻のミリ秒>を取得する。vはキャッシュの固定を避けるための値であり、DBのバージョン番号ではない。
  • 読み込み後はメモリ上の配列で表示・検索する。GitHub Actionsで配布データが更新されても、開いた画面で店舗DBを定期的に再取得する処理はない。新しい配布情報はページの再読み込みで取得する。30秒周期の時計更新・5分のルートキャッシュ期限は店舗DBの更新間隔ではない。
  • HTTPエラー、通信・JSON解析の例外、配列でない応答は空配列として扱う。各レコードの必須情報が不正ならその店を除外し、有効な同一IDは先頭の1件を採用する。旧localStorageの店舗情報や前回表示したDBからの復元は行わない。
  • 現行UIには店舗DBの読込中／失敗の専用表示や再試行ボタンがなく、空配列の場合は通常の0件表示となる。通信・解析の例外はコンソールへ記録し、再読み込みで再取得する。これは6.3のバッチ更新時の既存ファイル保持とは別の動作である。
  • ブラウザでは配布JSONを読み取るだけで、配布元への書込みやファイル出力は行わない。3.7のJSON操作UI撤去によって、自動更新・配信に必要なJSONファイルやスキーマを削除するものではない。

7. ルート・所要時間と到着予測（2026-10-18改訂）

  • 所要時間はすべて将来の予測なので「約」を付ける。「実測」「正確な到着時間」とは表示しない。
  • Googleの現行Routes APIを優先し、自動車検索はroutingPreference=TRAFFIC_AWARE_OPTIMALとdepartureTimeを指定してdurationMillisを取得する。利用不可の場合は既存Directions APIに切り替える。互換APIの自動車検索はdrivingOptions.departureTimeとtrafficModel=bestguessを指定する。duration_in_trafficが返れば通常のdurationより優先し、「Google交通予測・渋滞考慮」と表示する。取得できなければ「概算・渋滞情報なし」とする。
  • Googleの1区間の応答待ちは20秒。Routes APIが失敗したら互換Directions APIを試す。OSRMは開始間隔を1.1秒以上空け、待機を含め15秒で打ち切って距離モデルへ切り替える。徒歩はrouting.openstreetmap.de/routed-foot、自転車はrouted-bike、自動車はrouter.project-osrm.orgを使う。返却durationは秒から分へ切り上げる。
  • 巡回は最大8店舗。交通予測の返却条件を満たすため区間ごとに検索し、各区間の予測所要時間を次の区間の出発日時へ加算する。全区間・一部区間の渋滞考慮を区別する。店内滞在時間と開店待ち時間は含めない。
  • 公共交通はtransitOptions.departureTimeを指定する。取得できない場合は距離モデルの概算とし、自動車の経路を乗換ルートとして表示しない。
  • APIキー未設定時は、車・徒歩・自転車の対応OSRMサービスで形状とdurationを取得する。交通情報は含まないため概算とする。一般道優先と公共交通は非対応の道路経路を表示せず、選択モードの速度モデルから全区間を概算する。距離モデルの経路線は破線。
  • 出発時刻指定が現在より前なら、Googleに過去時刻を送れないため翌日の同時刻とする。
  • 単店検索の結果は同じ条件の一覧・地図ピンへ反映する。巡回結果は合計移動時間で最終店への到着を示すが、一覧の各店は出発地からその店への単独移動時間のままであり、巡回途中の到着時刻一覧ではない。日付をまたぐ到着と深夜営業を考慮する。指定出発時刻の翌日補正はAPI向け日時に適用し、営業時間の曜日別判定までは行わない。
  • 新しい店舗選択、出発地・手段・指定時刻の変更時は古い検索を中止・破棄する。閉じたカードを古い応答で再表示しない。
  • 時計更新だけでは課金APIを自動再呼出ししない。カードに情報取得時刻を表示し、最新情報は店舗の再選択で再取得する。単店結果だけを保存する一覧用のキャッシュは、出発地・店舗IDと座標・移動手段・地図エンジン・出発時刻の方式と指定値をキーとし、5分で失効する。失効後は距離モデルへ戻し、自動でルートAPIを呼び直さない。
  • 地図ピンは上位200件まで表示し、件数超過を案内する。一覧は120件ずつ追加表示できる。
  • 出発時刻の指定方式・時刻はlocalStorageに保存する。利用者向けJSON読込・書き出しは提供せず、配布JSONは実行時に検証・正規化する。旧版の保存済み店舗情報は適用しない。

参考: Google Routes APIの交通予測、Google Directionsの交通予測と返却条件、OSRM API。Googleの利用可否・料金・地域ごとの対応は利用者のAPI設定と提供条件に依存する。APIキーをブラウザへ入力するとGoogleへ送信されるため、HTTPリファラー制限・API制限を設定する。

8. 店舗別販売品目の確認とロゴ管理（2026-10-18改訂）

8.1 確認状態と検索

商品分類は店舗別の公式販売案内・取扱カテゴリ・フロア情報に限定する。系列名から標準品目を保証しない。買取専用・レンタル専用、非取扱項目、サイト共通の通販ナビは販売情報として採用しない。掲載品目は現在の実在庫を保証しない。

  • confirmed: 各構成店舗の対象となる公式掲載情報を取得できた。全商品・在庫・全詳細分類の確認済みという意味ではない。
  • partial: 一部の構成店・分野・フロア見出し・紹介文だけを確認できた。通常ゲオについてモバイル部門だけ確認できた場合も含む。
  • unverified: 使える店舗別の販売情報が未確認。取扱なし・非営業を意味しない。自動生成の分類は空配列にする。
  • user_edited: 旧データ形式との互換用の分類状態。公式情報とは表示しない。現行UIでは編集を作成せず、旧localStorageの編集も読み込まない。

「ゲーム」だけの公表では親retro_gameのみを保持し、レトロ・現行機の両方を追加しない。「ホビー」から全詳細を追加することもしない。親から全詳細へ展開する旧互換動作は廃止する。

全27詳細を選択したORでは未確認店も表示する。個別詳細の検索は明記された詳細だけを対象とする。ORで親の全詳細を選択した場合は、親だけ公表された店も含む。ANDは選択した全詳細が明記されている場合だけ一致とする。

8.2 JSON構造

scripts/assortment_evidence.jsonは更新元の安定IDをキーにしたオブジェクト。値は次の構造とする。

{
  categories: CategoryId[], subCategories: SubCategoryId[],
  status: "confirmed" | "partial",
  sources: [{url: string, checkedAt: string, labels: string[]}]
}

urlはHTTPSの公式店舗ページ・店舗別API、または店舗名ごとの販売欄を持つ公式一覧（じゃんぱらはhttps://www.janpara.co.jp/shopinfo#sales）、checkedAtは当該内容を確認したUTC日付（YYYY-MM-DD）、labelsは分類根拠になった公式の品目表記。取得失敗やキャッシュ再利用で日付を新しい日に書き換えない。

最終DBのassortmentSourcesは各出典に構成店舗のname:string、chain:ChainId、その出典で確認したcategories:CategoryId[]・subCategories:SubCategoryId[]を加えた配列。必須項目はこの7項目。例（URLは形式説明用）:

{
  "name": "ゲオモバイル サンプル店", "chain": "general_game",
  "categories": ["pc_junk"], "subCategories": ["sub_smartphone"],
  "url": "https://geo-mobile.jp/store/00000.html",
  "checkedAt": "2026-10-18", "labels": ["中古・新品携帯電話販売"]
}

併設ピンの出典は店名付きで表示する。チェーンをOFFにしたら、その構成店の商品分類と出典も除外し、別の店の取扱商品として残さない。店舗別の編集UIと端末保存は3.7のとおり撤去した。選択する詳細ジャンルが0件ならOR・ANDとも一致店舗は0件。
